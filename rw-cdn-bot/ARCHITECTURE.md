# Как устроен код

Документ для разработчика, который впервые открыл проект. Читается сверху вниз минут за
двадцать; после этого понятно, куда лезть за любой правкой.

---

## 1. Что вообще делает эта система

Telegram-бот продаёт услугу и **сам её выполняет**. После подтверждённой оплаты он заходит
по SSH на сервер клиента, настраивает там nginx и Remnawave Node, создаёт объекты в панели
Remnawave, выпускает сертификат и CDN-ресурс в Yandex Cloud, прописывает DNS и проверяет,
что связка работает.

Итоговая схема трафика клиента (то, ради чего всё):

```
Клиент → CDN Domain → Yandex Cloud CDN → Origin Domain → Origin Server
       → Nginx :443 → 127.0.0.1:2090 → Remnawave Node / Xray
```

Ключевое отличие от обычного «бота-магазина»: **основная работа происходит после оплаты и
занимает минуты**, а не миллисекунды. Отсюда вся архитектура — очередь, воркер, пошаговый
конечный автомат, повторы, паузы.

### Терминология (важно, путается постоянно)

| Термин | Что это |
|---|---|
| **Origin Server** | машина клиента, VPS. В коде: `origin_servers`, `origin_ip`, `origin_domain` |
| **Remnawave Node** | объект **внутри панели** Remnawave |
| **Remnanode** | Docker-контейнер, который ставится **на** Origin Server |
| **Origin Domain** | скрытый домен, A-запись на IP сервера |
| **CDN Domain** | публичный домен, CNAME на Yandex CDN — то, куда подключаются клиенты |

Origin Server и Remnawave Node — разные сущности. Нода живёт на сервере, но это не одно и
то же.

## 2. Процессы

Три отдельных контейнера, у каждого свой `python -m`:

| Процесс | Точка входа | Что делает |
|---|---|---|
| `bot` | `app/main.py` | aiogram long polling + aiohttp-сервер вебхуков |
| `worker` | `app/workers/deployment_worker.py` | выполняет настройку из очереди |
| `broadcast` | `app/workers/broadcast_worker.py` | рассылки с ограничением скорости |

Плюс `postgres`, `redis` и одноразовый `migrate` (`alembic upgrade head` перед стартом).

**Почему воркер отдельно.** Настройка одного заказа — это 26 шагов, SSH-сессия и ожидания
DNS по несколько минут. Держать это внутри обработчика Telegram-апдейта нельзя: бот перестал
бы отвечать. Поэтому бот только ставит задачу в Redis, а воркер её забирает.

Из этого следует правило: **всё длительное — в воркере, всё быстрое — в боте**. Если
добавляешь операцию с SSH или облаком, она идёт через очередь.

## 3. Слои

```
app/bot/          — интерфейс: хендлеры, клавиатуры, FSM, тексты
app/services/     — вся логика: платежи, SSH, Remnawave, Yandex, DNS, деплой
app/repositories/ — доступ к данным, по одному классу на сущность
app/models/       — таблицы SQLAlchemy
app/core/         — шифрование, ошибки, повторы, логирование
app/config/       — настройки из окружения
```

Правило зависимостей — только вниз. Хендлер зовёт сервис, сервис зовёт репозиторий,
репозиторий трогает модели. Обратных импортов нет.

`app/services/` — самая большая часть, и это нормально: здесь живёт то, за что платят.

## 4. Путь заказа

```
CREATED → (оплата) → PAID → COLLECTING_DATA → DEPLOYING → ... → COMPLETED
                                                    ↓
                                        FAILED / waiting_*
```

Пошагово:

1. **Покупка** (`bot/handlers/purchase.py`). Пользователь выбирает тариф, создаётся `Order`
   с **замороженной ценой** — если админ поменяет цену завтра, этот заказ не подорожает.
2. **Оплата** (`bot/handlers/payment.py`). Создаётся платёж у Platega или ЮKassa, клиент
   уходит по ссылке. Кнопка «Я оплатил» — **чисто информационная**, ничего не подтверждает.
3. **Вебхук** (`app/webhooks/server.py`). Провайдер стучится на `/webhooks/platega` или
   `/webhooks/yookassa`. Здесь заказ помечается оплаченным и задача уходит в очередь.
4. **Сбор данных** (`bot/handlers/collect.py`). FSM спрашивает URL панели, токен, IP, SSH,
   домены, доступ к Yandex Cloud, режим DNS.
5. **Настройка** (`services/deployment/service.py`) — 26 шагов в воркере.
6. **Готово**: клиенту уходит подписка, заказ закрывается.

## 5. Деньги: три правила, которые нельзя нарушать

Это место, где ошибка стоит реальных денег. Логика в `services/payments/service.py`.

**Правило 1. Оплата подтверждается только вебхуком, и только после перепроверки.**
Мы не верим телу вебхука на слово: после разбора делается запрос к API провайдера
(`fetch_status`) и статус сверяется. Иначе подделанный вебхук зачёл бы неоплаченный заказ.

**Правило 2. Идемпотентность.** Провайдер может прислать вебхук 2, 5, 20 раз — это норма.
В `payment_events` стоит уникальный индекс `(provider, event_key)`; повторное событие
вставиться не может и обработка тихо прекращается. Проверь сам:
`tests/test_payment_idempotency.py`.

**Правило 3. Деньги — только целые копейки.** В базе `BigInteger`, никаких `float`.
Platega работает в рублях, конвертация — в одном месте (`payments/base.py`) через `Decimal`.
Если увидишь в коде `float` рядом с суммой — это баг.

**Вебхук не запускает настройку.** Он делает минимум: проверил → одна транзакция в БД →
задача в очередь → `200`. Никаких SSH и облачных вызовов внутри обработчика: провайдер ждёт
ответа секунды, а настройка идёт минуты.

## 6. Движок настройки — самая важная часть

`services/deployment/service.py`, ~700 строк. Разберём по механике.

### Шаги

`steps.py` — плоский список из 26 имён в порядке выполнения:

```
validate_data · check_origin · prepare_origin · configure_firewall · configure_sysctl
configure_swap · install_docker · install_nginx · configure_site · configure_origin_dns
verify_origin_dns · configure_ssl · configure_nginx · create_remnawave_profile
create_remnawave_node · install_remnanode · create_remnawave_host · create_yandex_certificate
configure_acme_dns · verify_certificate · create_yandex_cdn · get_yandex_cname
configure_dns · verify_dns · health_check · complete
```

Каждому имени соответствует метод `_step_<имя>`. Движок идёт по списку и вызывает их по
очереди. Хочешь добавить шаг — добавь имя в `STEP_ORDER`, заголовок в `STEP_TITLES` и метод.
Больше нигде трогать не нужно.

Состояние каждого шага пишется в таблицу `deployment_steps`.

### Идемпотентность

Воркер может упасть и перезапуститься в любой момент. Поэтому:

* шаги со статусом `SUCCESS` при повторном запуске **пропускаются**;
* перед созданием любого ресурса выполняется поиск существующего — профиль ищется по имени,
  нода по адресу, host по адресу, сертификат по домену, CDN-ресурс по домену.

То есть повторный прогон ничего не дублирует. Это не «приятный бонус», а обязательное
свойство: без него упавший воркер плодил бы сертификаты и CDN-ресурсы.

### Три вида ошибок

Разница между ними определяет поведение системы, и это главное, что надо понять:

| Тип | Что означает | Что делает движок |
|---|---|---|
| `TransientError` | временно: таймаут, 5xx, ресурс ещё не готов | повторяет `5s → 15s → 30s` |
| `PermanentError` | повторять бессмысленно: битый ключ, занятый порт, нет прав | сразу `FAILED` |
| `WaitingError` | ждём внешнее событие: DNS не разошёлся, сертификат валидируется | паркует заказ, не считая это ошибкой |

`WaitingError` — не провал. Заказ уходит в `waiting_dns` / `waiting_certificate`, попадает в
отложенную очередь и сам возобновляется через 180 секунд. Клиент видит «⏸», а не «❌».

Отдельный случай — `ReauthRequired` (наследник `PermanentError`): доступ к Yandex Cloud
умер. Заказ уходит в `waiting_reauth`, **повторов нет** (долбить мёртвую сессию бессмысленно),
клиента просят прислать данные командой `/reauth <id>`.

**Когда добавляешь код — обязательно выбери правильный тип ошибки.** Кинуть `TransientError`
на битый ключ значит потратить минуту на бессмысленные повторы; кинуть `PermanentError` на
сетевой таймаут значит сломать заказ из-за моргнувшей сети.

### Прогресс

Клиенту не сыплются уведомления. Есть **одно** сообщение, которое редактируется
(`bot/notifications.py` + `deployment/progress.py`). ID сообщения хранится в заказе.

## 7. Внешние интеграции

### Remnawave (`services/remnawave/`)

* `endpoints.py` — все пути в одном месте. **Эндпоинты не выдумываются**: если операции нет
  в документированном API, поднимается `RemnawaveUnsupportedOperation`, а не подбирается
  правдоподобный URL. Пути одинаковы в API v2 и v3.
* `dialects.py` — **всё, чем v2 отличается от v3**: имя поля в `/keygen`, регистр
  `xHttpExtraParams`/`xhttpExtraParams`, наличие `nodes` у host, коды успеха. Версия
  определяется одним запросом `GET /system/metadata` — он есть только в v3, поэтому его
  отсутствие и есть ответ «это v2». Результат хранится в `remnawave_instances.api_version`
  и может быть закреплён вручную.
* `templates.py` — фиксированные параметры схемы. **Единственное место**, где заданы путь,
  порт, mode, padding, ALPN, отпечаток. Имена полей выбирает диалект, значения — этот модуль.
* `client.py` — идемпотентные `ensure_*`, ответы разворачиваются из `{"response": ...}`
  (конверт одинаков в обоих мажорах), ошибки показываются по полю `message`, а не сырым JSON.

**Про `templates.py` отдельно.** Эти значения должны совпадать в трёх местах сразу: inbound
Xray, location в nginx и host в Remnawave. Рассинхрон даёт не ошибку, а молчаливый обрыв
соединения — отладить тяжело. Поэтому все три читают отсюда, и есть тест, который сверяет
`extra` у inbound и у host байт в байт. Меняешь параметр — меняй только здесь.

**SECRET_KEY ноды** ищется по цепочке: значение, введённое админом → поля объекта ноды →
`GET /keygen/pub-key`. Не нашлось — деплой честно останавливается и просит ввести вручную,
а не генерирует нерабочий compose.

### Yandex Cloud (`services/yandex/`)

* `auth.py` — три способа авторизации за общим интерфейсом: ключ сервисного аккаунта (JWT
  PS256), OAuth-токен, cookie-сессия. Первые два документированы, третий — нет.
* `cookies.py` — разбор пяти форматов экспорта cookie, фильтр по доменам, отброс просроченных.
  Банка хранит каждую cookie отдельно (имя, значение, домен, срок), поэтому `dumps()` переживает
  переход бот → воркер без потери домена и срока, а заголовок собирается уже под конкретный хост.
* `client.py` — Certificate Manager, CDN, Cloud DNS + `check_access()`.

**Про `check_access()`.** Права проверяются **эмпирически** — реальным дешёвым запросом в
каждый сервис, а не разбором списка ролей. Проверка останется верной, даже если Yandex
переименует роль. `403` → нет прав (постоянная ошибка с именем роли), `5xx` → сервис лежит
(временная). Разделять эти случаи важно: иначе авария Yandex выглядела бы как «клиент не
выдал права».

Вызывается дважды: при вводе данных и на шаге `validate_data`. Смысл — упасть на первом
шаге, а не в середине, когда сервер уже перенастроен.

### DNS (`services/dns/`)

Три провайдера за общим интерфейсом: Cloudflare API, Yandex Cloud DNS, вручную.
Cloudflare-записи создаются **всегда с выключенным проксированием** — оранжевое облако
сломало бы схему.

Проверка распространения — настоящий resolve через публичные резолверы (1.1.1.1, 8.8.8.8,
77.88.8.8), а не «мы создали запись, значит всё хорошо».

### SSH (`services/ssh/client.py`)

asyncssh. Секреты пишутся через SFTP, **не** через командную строку — иначе они попали бы в
`ps` и в логи. `known_hosts=None`, потому что машины клиентов ни в каком known_hosts не
лежат.

### Node installer (`services/deployment/node_installer.py`)

Установка Remnanode вынесена в отдельный модуль, а не в bash-скрипт: нужны SFTP-запись и
разбор состояния контейнера. Поддерживает два формата переменных (`NODE_PORT`+`SECRET_KEY` и
старый `APP_PORT`+`SSL_CERT`) с автоматическим откатом, если образ ждёт старые имена.

## 8. Секреты

**Что шифруется** (Fernet, ключ только в `.env`, в БД его нет): SSH-ключ, SSH-пароль, токен
Remnawave, ключ сервисного аккаунта Yandex, OAuth-токен, токен Cloudflare.

**Что не хранится вообще**: cookie-сессии Yandex. Они лежат в Redis
(`services/vault.py`) — зашифрованные, с TTL не длиннее часа и не длиннее самой сессии — и
удаляются сразу после шага `configure_dns` (последнего, которому может понадобиться Yandex:
DNS-провайдером бывает Cloud DNS), при любом терминальном исходе и по TTL, если воркер упал.

**Сообщения с секретами удаляются из чата.** Обратно секрету не отдаются никогда — в
админке видно только маску вида `abcd…wxyz`.

**Логи проходят через фильтр** (`core/logging.py`), который вырезает токены и заголовки
авторизации. Клиенту показывается короткая причина ошибки, полный traceback остаётся в логах
и в `audit_logs`.

## 9. Правила проекта

Их несколько, и они не стилистические — каждое закрывает конкретную дыру.

**Никакого каскада.** Ни зарубежного выхода, ни geoip/geosite-маршрутизации, ни foreign
node. Трафик уходит с Origin Server напрямую. Есть тест, который стережёт: если в
`STEP_ORDER` появится шаг со словом `cascade`, `foreign`, `geoip`, `geosite` или `exit`,
сборка упадёт.

**Порт Xray не открывается наружу.** `2090` слушает только `127.0.0.1`. Health check
проверяет это отдельно и не пропускает заказ, если порт торчит в мир.

**Ничего не хардкодится**, кроме технических параметров схемы. IP, домены, токены, цены,
Telegram ID, CNAME от Yandex, UUID Remnawave — всё из настроек, БД или API.

**Эндпоинты не выдумываются.** Если API не документирован — либо явная ошибка, либо
эмпирическая проверка с отказом при неподтверждении (как автоопределение cookie-обмена:
кандидат засчитывается, только если вернул JSON с токеном).

**`400` на пути xHTTP от обычного curl — это норма**, а не поломка. Значит запрос дошёл до
Xray, а curl просто не является VLESS-клиентом.

## 11. Грабли

**`docker compose restart` не пересобирает образ.** После правки кода нужен
`docker compose up -d --build`, иначе крутится старая версия.

**Порядок роутеров в aiogram имеет значение.** Хендлер с фильтром состояния перехватит
сообщение раньше, чем хендлер команды без фильтра. Поэтому `/reauth` и `/testorder` вынесены
на роутеры, включённые **до** FSM сбора данных. Если добавляешь команду, которая должна
работать в середине опроса, — туда же.

**Префиксы callback-данных пересекаются.** `F.data.startswith("pay:")` перехватит и
`pay:check:...`, если зарегистрирован раньше. Смотри порядок или используй точное совпадение.

**`pydantic-settings` разбирает поля типа `list` как JSON** — до того, как отработают
валидаторы. Поэтому все списочные настройки (`ADMIN_IDS`, `YOOKASSA_ALLOWED_IPS`,
`DEPLOY_RETRY_DELAYS`) объявлены строками, а списки отдаются свойствами. Не меняй их тип на
`list` — процесс упадёт на старте. Прикрыто тестами в `test_settings.py`.

**Сертификат и CDN-ресурс должны быть в одном каталоге Yandex**, иначе `folder ids of user
and certificate don't match`. Проверяется перед созданием ресурса.

## 12. Тесты

```bash
pip install -e ".[dev]"
pytest
```

17 файлов. Что покрыто: вебхуки платежей и идемпотентность, создание заказа, конечный
автомат настройки, клиент Remnawave, node installer, клиент Yandex и проверка прав, три
способа авторизации, разбор cookie, хранилище секретов, проверка DNS, повторы, шифрование,
права админа, конфиг nginx и firewall, разбор настроек.

**Что стоит понимать про эти тесты:** они проверяют логику и контракты, но ни один из них не
поднимает настоящий сервер. Реальный деплой на живой Origin Server ничем не заменить —
первый прогон всегда вскрывает что-то, чего юнит-тесты не видят. Для этого есть
`/testorder`: заказ без оплаты, дальше всё как у настоящего клиента.
